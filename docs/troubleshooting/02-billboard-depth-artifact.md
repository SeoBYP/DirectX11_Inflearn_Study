# 빌보드 풀숲의 앞뒤가 뒤집혀 보이는 문제 — 가설 두 개를 측정으로 기각하기

> **한 줄 요약** — 뒤쪽 풀이 앞쪽 풀보다 앞에 보이는 현상을 두고 "블렌드 상태 누수"와 "깊이 테스트 미동작"을 의심했으나, 픽셀 diff 측정으로 **둘 다 기각**했다. 깊이값을 색으로 출력해 확인한 결과 **무더기 하나가 깊이 하나를 공유하는 빌보드 기법 자체의 한계**였다.

---

## 1. 시작한 배경

`BillBoardDemo` 를 실행하면 풀숲이 그려지는데, **뒤쪽 무더기의 잎이 앞쪽 무더기 위에 얹힌 것처럼** 보였다. 밑동에는 계단 모양의 하드한 직사각형 경계가 드러났다.

이런 증상은 보통 알파 블렌딩된 물체를 정렬 없이 그릴 때 나온다. 그래서 처음에는 "순서 의존 아티팩트"라고 판단했다.

먼저 코드에서 확인 가능한 사실부터 모았다.

| 확인 대상 | 결과 |
|---|---|
| 깊이 버퍼 생성·바인딩 | `Graphics.cpp:16-18` — 매 프레임 `OMSetRenderTargets` + `ClearDepthStencilView` 정상 |
| 셰이더의 깊이 상태 | 셰이더 33개 전체에 `DepthStencilState` 정의도 `SetDepthStencilState` 호출도 **없음** → D3D11 기본값 사용 |
| 빌보드 패스의 블렌드 상태 | `28. BillboardDemo.fx` 의 `pass P0` 가 `SetBlendState` 를 **설정하지 않음** |
| 투명 처리 방식 | 알파 블렌딩이 아니라 **알파 테스트** (`if (diffuse.a < 0.3f) discard;`) |

Effects11은 패스마다 상태를 초기화하지 않는다. 즉 이 패스는 **직전에 디바이스에 걸려 있던 상태를 그대로 물려받는다.** 여기서 가설이 나왔다.

## 2. 설계

셰이더가 `D3DCompileFromFile` 로 **런타임 컴파일**된다는 점을 확인했다. `.fx` 만 고치면 리빌드 없이 실행할 수 있어, 가설 하나당 수정 → 실행 → 캡처를 빠르게 반복할 수 있었다.

검증 기준을 먼저 정했다. **같은 카메라 위치에서 캡처한 두 화면의 픽셀 diff**로 판정한다. "보기에 나아졌다"는 판정하지 않는다.

## 3. 작업 내용

### 가설 A — 블렌드 상태 누수

앞 패스에서 켜진 알파 블렌딩이 남아 순서 의존이 생긴다고 봤다. 패스에 상태를 명시했다.

```hlsl
BlendState NoBlend        { AlphaToCoverageEnable = false; BlendEnable[0] = false; };
DepthStencilState DepthDefault { DepthEnable = true; DepthWriteMask = ALL; DepthFunc = LESS; };

pass P0
{
    SetBlendState(NoBlend, float4(0,0,0,0), 0xFF);
    SetDepthStencilState(DepthDefault, 0);
    ...
}
```

```
다른 픽셀: 14 / 480000  (0.00%)
최대 채널 차이: 18
변화 bbox: (793, 593, 800, 600)     ← 우하단 7×7 구석뿐
```

**기각.** 디바이스에는 이미 블렌딩이 꺼지고 깊이가 켜진 기본 상태가 걸려 있었다. 내 가설은 틀렸다.

### 가설 B — 깊이 테스트가 실제로는 안 걸린다

기본값이라고 문서상 그렇다는 것뿐, 실제로 동작하는지는 별개다. **깊이 테스트를 꺼서 비교**했다. 원래 켜져 있지 않았다면 껐을 때도 화면이 같아야 한다.

```
깊이 ON vs OFF
  다른 픽셀: 39813 / 480000  (8.29%)
  변화 bbox: (0, 225, 800, 359)     ← 풀숲 영역 전체
```

**기각.** 8.29%가 달라졌다는 것은 깊이 테스트가 결과에 관여하고 있다는 뜻이다. 정상 작동 중이었다.

### 가설 C — 텍스처의 불투명한 검은 픽셀

풀 텍스처 밑동에 알파는 통과하는데 색이 검은 픽셀이 있어 검은 사각형으로 찍히는 것 아닌가. 텍스처를 직접 분석했다.

```
grass.png  1200x1200  RGBA
알파 < 0.3 인 픽셀: 70.0%
알파 통과(>=0.3) 픽셀 중 거의 검정(RGB<0.15)인 비율: 0.0%
```

**기각.** `discard` 는 정상 동작하고, 통과한 픽셀 중 검은 것은 없다.

### 확정 — 깊이를 색으로 출력

추측을 멈추고 깊이값 자체를 보기로 했다. 정점 셰이더에서 뷰 공간 깊이를 넘기고 픽셀 셰이더에서 색으로 출력했다.

```hlsl
float4 viewPos = mul(position, V);
output.position = mul(viewPos, P);
output.viewZ    = viewPos.z;
...
float d = saturate(input.viewZ / 25.0f);
return float4(1.0f - d, frac(input.viewZ * 0.4f), d, 1.0f);
```

**각 무더기가 완전한 단색으로 나왔다.** 무더기 안에 잎이 수십 장 그려져 있어도 깊이값은 하나뿐이었다.

원인을 코드에서 확인했다.

```cpp
// Billboard.cpp:74-77 — 정점 4개가 모두 같은 world 위치
_vertices[_drawCount * 4 + 0].position = position;
_vertices[_drawCount * 4 + 1].position = position;
_vertices[_drawCount * 4 + 2].position = position;
_vertices[_drawCount * 4 + 3].position = position;
```

```hlsl
// 28. BillboardDemo.fx — 셰이더에서 right/up 으로 펼쳐 사각형을 만든다
float3 forward = position.xyz - CameraPosition();
float3 right   = normalize(cross(up, forward));
position.xyz += (input.uv.x - 0.5f) * right * input.scale.x;
position.xyz += (1.0f - input.uv.y - 0.5f) * up * input.scale.y;
```

`right` 는 시선 방향과 수직이다. 결과적으로 **한 무더기가 카메라를 향한 평면 한 장**이고, 그 위의 잎들은 전부 같은 깊이로 눌린다. 잎마다의 앞뒤 관계는 **애초에 존재하지 않는다.**

### 두 번째 원인 — 지면이 없다

밑동의 계단형 하드 컷은 별개 원인이었다.

```cpp
// BillBoardDemo.cpp:98 — 중심을 높이의 절반에 두어 밑변이 정확히 y=0 에 놓인다
obj->GetBillboard()->Add(Vec3(position.x, scale.y * 0.5f, position.y), scale);
```

모든 무더기의 밑변이 `y=0` 인데, **이 데모에는 지면이 없다.** `Terrain.h` 가 include 되어 있지만 `Terrain` 컴포넌트는 한 번도 추가되지 않는다. `y=0` 은 거리에 따라 화면상 다른 높이에 투영되므로(가까울수록 아래, 멀수록 수평선 쪽), 밑변이 검은 배경과 만나 **계단 모양**이 된다. 먼 무더기일수록 밑변이 화면 위쪽에 와서 "가까운 풀 위에 먼 풀이 얹힌" 인상을 강화한다.

## 4. 고민한 부분과 선택

원인이 기법의 한계라면 해법도 기법 차원이다. 세 가지를 검토했다.

| 대안 | 효과 | 비용 / 제약 |
|---|---|---|
| **A. MSAA + AlphaToCoverage** | 알파 컷오프 경계를 커버리지로 분산해 계단 완화 | **현재 MSAA가 꺼져 있다** (`SampleDesc.Count = 1`, 스왑체인·깊이버퍼 모두). 먼저 켜야 하고, 그만큼 대역폭·메모리 비용이 붙는다 |
| **B. 잎 단위 지오메트리 분리** | 잎마다 깊이가 생겨 원인 자체를 제거 | 정점 수와 드로우 데이터가 크게 늘어난다. 빌보드를 쓰는 이유(비용 절감)를 포기하는 셈 |
| **C. 뒤→앞 정렬 후 알파 블렌딩** | 순서 문제 해소 | 카메라가 움직일 때마다 500개를 매 프레임 정렬해야 한다 |

**우선순위를 "지면 추가 → A → B" 로 잡았다.**

## 5. 선택 이유

- 두 원인 중 **지면 부재는 비용이 거의 0인데 눈에 보이는 개선이 크다.** `Terrain.h` 는 이미 include 되어 있고 `CollisionDemo` 에 사용 예도 있다. 가장 싼 것부터 하는 게 맞다.
- A는 알파 컷아웃 폴리지의 업계 표준 해법이다. 다만 **MSAA가 꺼져 있다는 사실을 확인하기 전이었다면 A를 먼저 적용하고 "효과가 없다"며 헤맸을 것이다.** 상태를 먼저 확인한 것이 시간을 아꼈다.
- B는 원인을 정면으로 없애지만, 빌보드를 채택한 이유 자체를 무너뜨린다. 풀처럼 개체 수가 많은 대상에는 맞지 않는다.
- C는 이 규모에서는 가능하지만, 개체가 늘어나면 정렬 비용이 먼저 터진다. 확장성이 없다.

## 6. 결과

**원인 규명까지가 이번 작업의 결과다. 수정은 적용하지 않았다.**

| 항목 | 판정 | 근거 |
|---|---|---|
| 블렌드 상태 누수 | **아님** | 상태 명시 전후 픽셀 차이 0.00% (14/480000) |
| 깊이 테스트 미동작 | **아님** | 껐을 때 8.29% 변화 (39813/480000) |
| 텍스처의 검은 불투명 픽셀 | **아님** | 알파 통과 픽셀 중 RGB<0.15 비율 0.0% |
| 알파 테스트 동작 | **정상** | 풀 픽셀만 빨강 출력 시 잎 실루엣이 정확히 유지됨 |
| 무더기당 깊이 1개 | **확정** | 깊이 시각화에서 무더기가 완전 단색 |
| 지면 미배치 | **확정** | `Terrain.h` include 만 있고 컴포넌트 미사용 |

가설 세 개를 세워 셋 다 측정으로 기각했다. 코드만 읽고 "이게 원인 같다"에서 멈췄다면 **블렌드 상태를 명시하는 틀린 수정을 넣고 문제가 남았을 것이다.**

## 남은 것

- **지면 추가는 시도했으나 실패했다.** `Mesh::CreateQuad()` 는 XY 평면 쿼드라 X축으로 눕히면 법선과 와인딩이 함께 뒤집힌다. `+90°` 는 수평선 근처만 그려지고 `-90°` 는 뒷면 컬링으로 완전히 사라졌다. 래스터라이저 컬링 모드를 끄거나 `Mesh::CreateGrid()` 를 쓰는 쪽이 다음 시도다.
- MSAA를 켠 뒤 AlphaToCoverage가 실제로 개선하는지는 **미실측**이다.
