### 왜 이 프로젝트를 넣었는가

엔진을 쓰는 것과 엔진이 무엇을 하는지 아는 것은 다릅니다.
이 프로젝트는 **정점 데이터를 GPU에 올려 화면에 픽셀이 찍히기까지의 전 과정**을,
엔진이 대신 해 주지 않는 레벨에서 직접 다뤄 본 기록입니다.

`MeshRenderer` 하나를 만들기 위해 정점 버퍼·입력 레이아웃·상수 버퍼·셰이더 패스를 각각 준비해야 했고,
그 경험 덕분에 상용 엔진에서 드로우콜이나 배칭 이야기가 나올 때
**무엇이 비용인지, 왜 그런 제약이 있는지**를 구조 수준에서 이해하고 접근할 수 있습니다.

### 직접 구현하며 확인한 것

| 영역 | 내용 |
|---|---|
| **렌더 파이프라인** | 정점/인덱스 버퍼 → 입력 레이아웃 → 상수 버퍼 → 셰이더 패스 → 드로우콜의 전 과정 |
| **엔진 아키텍처** | GameObject / Component 구조, 씬 그래프, 리소스 매니저, 렌더 매니저 |
| **조명 · 재질** | Ambient / Diffuse / Specular / Emissive 분해, 노멀 매핑 |
| **모델 · 애니메이션** | Assimp 모델 임포트, 자체 바이너리 포맷 변환, 스키닝 애니메이션, 트위닝 |
| **드로우콜 최적화** | 인스턴싱, StructuredBuffer / RawBuffer / TextureBuffer 를 통한 GPU 데이터 전달 |
| **공간 · 충돌** | AABB · OBB · Sphere, Point Test / Intersection / Raycast |

### 구조 요약

```
Engine (정적 라이브러리, 소스 55 · 헤더 59)
 ├ 코어      Game · Graphics · Viewport · TimeManager · InputManager
 ├ 씬        Scene · SceneManager · GameObject · Transform · Component
 ├ 렌더링    Shader · Pass · Technique (FX11) · Material · Texture · Mesh
 ├ 버퍼      Vertex · Index · Constant · Structured · Raw · Texture · Instancing
 ├ 인스턴싱  InstancingManager → 각 렌더러의 RenderInstancing()
 ├ 충돌      AABB · OBB · Sphere Collider
 └ 모델      Model · ModelMesh · ModelAnimation · ModelRenderer · ModelAnimator

AssimpTool  FBX 등을 런타임 파싱 없이 자체 포맷(.mesh / .clip)으로 사전 변환

```

Unity의 컴포넌트 모델을 참고한 구조로, `GameObject::Update()` 가 각 컴포넌트의 `Update()` 를 호출하고
렌더러 컴포넌트가 그 안에서 상수 버퍼를 채우고 드로우콜까지 수행합니다.

### 기술적 도전과 해결 (요약)

엔진 코드 자체는 강의를 따라간 것입니다. **어필 포인트는 그 코드를 3년 뒤 새 툴체인에서 다시 굴러가게 만드는 과정**에 있습니다. 세 건 모두 전후를 비교할 수 있는 측정값을 남겼습니다.

- **애니메이션이 멈춰 있던 원인이 애니메이션 코드가 아니었던 건** — 스프라이트가 정지해 방금 구현한 `Animator` 를 의심했지만, 호출 경로를 위에서부터 대조하니 진입점의 블로킹 `GetMessage` 루프가 원인이었다. 고치기 전에 **창에 메시지를 주입해 화면이 살아나는 것을 먼저 확인**해 원인을 확정했다. 서로 다른 프레임 **1/8 → 4/8**(키프레임 수와 일치), 변경량 2줄.
  → [상세](troubleshooting/01-blocking-message-loop.md)

- **빌보드 풀숲의 앞뒤가 뒤집혀 보이는 문제** — "블렌드 상태 누수", "깊이 테스트 미동작" 가설을 픽셀 diff로 **둘 다 기각**(각각 **0.00%**, **8.29%** 변화). 깊이값을 색으로 출력해 **무더기당 깊이가 하나**뿐인 빌보드 기법의 한계임을 확정했다. 코드만 읽고 판단했다면 틀린 수정을 넣었을 것이다.
  → [상세](troubleshooting/02-billboard-depth-artifact.md)

- **3년 전 코드를 새 툴체인에서 되살리기** — v143→v145 이전 중 **병렬 빌드에서만 터지는 `LNK1104`** 와 **클린 클론에서만 무한 대기하는 빌드**를 찾아 고쳤다. 전자는 `#pragma comment(lib)` 가 빌드 시스템에 의존성을 알리지 않아서, 후자는 `xcopy` 가 대상 폴더 부재 시 되묻기 때문. 둘 다 산출물이 커밋되어 있어 그동안 드러나지 않았다.
  → [상세](troubleshooting/03-build-system.md)

### 이 과정에서 알게 된 것

- **증상과 원인은 대개 다른 계층에 있다.** "애니메이션이 안 움직인다"의 원인은 `WinMain` 의 메시지 루프였다.
- **가설은 측정으로 죽여야 한다.** 코드 근거까지 있던 첫 가설이 픽셀 차이 0.00%로 기각됐다.
- **렌더링 버그는 눈으로 판단하면 안 된다.** 깊이를 색으로 출력하고 나서야 원인이 확정됐다.
- **빌드 순서는 선언해야 생긴다.** `#pragma comment(lib)` 는 링커에게만 말한다.
- **"내 컴퓨터에서는 됩니다"는 클린 상태를 재현해야 없앨 수 있다.**

### 이 프로젝트의 범위 (명확히)

- **엔진 코드는 강의를 따라가며 작성한 것입니다.** 강의 범위를 넘어선 독자적인 시스템 설계는 없습니다. 위 「기술적 도전과 해결」은 코드 작성이 아니라 **재빌드·진단·수정** 과정입니다.
- **성능 측정 자료가 없습니다.** 프레임 타임·드로우콜·메모리를 측정한 적이 없어, 최적화 성과로 제시할 수치가 없습니다.
- 데모 36개 중 **씬 기반으로 실제 렌더링되는 것은 8개**이고, 나머지는 학습 중 구조를 바꾸면서 이전 렌더 경로가 주석 처리된 상태입니다.

## 2. 나올 만한 질문과 답변 방향

| 질문 | 답변 방향 |
|---|---|
| "강의 따라 친 건데 뭘 배웠나?" | 정직하게 인정하고, **"쓰는 것"과 "무엇을 하는지 아는 것"의 차이**로 전환. 블로그 32편을 근거로 제시. |
| "상수 버퍼가 뭔가?" | CPU가 매 드로우콜마다 셰이더에 넘기는 상수 데이터. 월드/뷰/프로젝션 행렬, 라이트·머티리얼 정보. 갱신 빈도별로 슬롯을 나누는 이유까지. |
| "드로우콜이 왜 비용인가?" | CPU→GPU 상태 전환과 커맨드 제출 오버헤드. 그래서 인스턴싱으로 같은 메시를 한 번에 그린다. 이 프로젝트의 `InstancingManager` 가 그 구조. |
| "AABB와 OBB의 차이는?" | AABB는 축 정렬이라 검사·갱신이 싸지만 회전 시 헐거워짐. OBB는 타이트하지만 SAT 기반이라 비싸다. |
| "성능은 얼마나 개선했나?" | **측정한 적이 없다고 정확히 답한다.** 대신 무엇을 측정했어야 하는지를 말할 수 있으면 좋다. |
| "Unity/Unreal에서 이 경험이 어떻게 쓰이나?" | 배칭·SRP Batcher·머티리얼 인스턴스가 무엇을 줄이는지 구조로 이해. 프로파일러 수치를 해석할 때 원인을 파이프라인 단계로 좁힐 수 있음. |

## 4. 이 프로젝트를 더 강하게 만들려면

지금은 "이해했다"까지만 증명됩니다. **"측정하고 개선했다"** 로 올리려면 다음 중 하나면 충분합니다.

1. **인스턴싱 전후 비교 측정** — 같은 오브젝트 N개를 개별 드로우 vs 인스턴싱으로 그려
   드로우콜 수와 프레임 타임을 같은 조건에서 측정. 이 저장소에 이미 두 경로가 다 있어 바로 가능합니다.
2. **비활성 렌더 경로 복구** — `ModelRenderer::Update()` / `ModelAnimator::Update()` 를 되살려
   개별 렌더 경로와 인스턴싱 경로를 나란히 비교. 1번 측정의 준비 작업이 됩니다.
3. **`Animation::Save` 의 텍스처 경로 저장 완성** — 현재 `TODO` 로 비어 있어 저장 후 로드하면
   텍스처가 유실됩니다. 작은 범위지만 "직접 고친 것"이 됩니다.
