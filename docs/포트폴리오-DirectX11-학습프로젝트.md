### 왜 이걸 공부했는가

상용 엔진은 렌더링을 잘 감춰 줍니다. 그래서 **드로우콜·배칭·머티리얼 인스턴스 같은 말을 쓰면서도 그 아래에서 무슨 일이 일어나는지는 모른 채** 개발할 수 있습니다.

프로파일러가 "드로우콜 300"이라고 말할 때 그게 왜 비용인지 구조로 설명하지 못하면, 최적화는 **인터넷에서 본 팁을 순서대로 시도해 보는 일**이 됩니다. 무엇을 줄이는 조치인지 모르니 효과가 없어도 이유를 알 수 없고, 효과가 있어도 다음에 재현하지 못합니다.

그래서 엔진이 감춰 주는 계층 — 정점 버퍼를 GPU에 올리고, 상수 버퍼로 행렬을 넘기고, 셰이더 패스를 골라 드로우콜을 부르기까지 — 을 한 번은 직접 만들어 보기로 했습니다.

**DirectX 11을 고른 이유**는 두 가지입니다. DX12·Vulkan은 커맨드 리스트·리소스 배리어까지 직접 다뤄야 해서 파이프라인 개념보다 API 사용법에 시간이 쏠립니다. 그리고 DX11은 렌더링만이 아니라 **컴포넌트 시스템·씬·리소스 매니저까지 한 프로젝트에서 만들어 볼 수 있는 규모**라, 상용 엔진의 개념이 실제로는 어떤 코드인지 확인하기에 적합했습니다.

### 직접 구현하며 확인한 것

| 영역 | 내용 |
|---|---|

| **엔진 아키텍처** | GameObject / Component 구조, 씬 그래프, 리소스 매니저, 렌더 매니저 |

### 공부하면서 얻은 것

추상적인 "이해했다"가 아니라, **무엇을 만들어 보고 무엇이 보이게 됐는지**로 적습니다.

- **드로우콜이 왜 비용인지 구조로 알게 됐습니다.** `InstancingManager` 를 만들어 보니 비용의 정체는 그리는 횟수가 아니라 **오브젝트마다 상수 버퍼를 갱신하고 파이프라인 상태를 바꾸는 것**이었습니다. 인스턴싱은 오브젝트별 데이터를 인스턴스 버퍼로 옮겨 상태 변경을 없애는 조치였습니다. 저장소에 개별 렌더 경로와 인스턴싱 경로가 **둘 다 남아 있어** 구조 차이를 코드로 비교할 수 있습니다.
  → Unity의 SRP Batcher · GPU Instancing · 머티리얼 인스턴스가 각각 무엇을 줄이는지 구분해 접근할 수 있습니다.

- **셰이더에 데이터를 넘기는 방법이 왜 여러 가지인지 알게 됐습니다.** ConstantBuffer / StructuredBuffer / RawBuffer / TextureBuffer 를 각각 써 보니 크기 제한 · 접근 패턴 · 갱신 빈도에 따라 선택이 갈렸습니다. 상수 버퍼 슬롯을 갱신 빈도별로 나누는 관행이 왜 생겼는지 납득했습니다.

- **컴포넌트 구조를 두 번 만들고 나서야 설계 의도가 보였습니다.** Chapter2에서 최소 구조를 만들고, Client에서 그 위에 렌더링 기법을 올렸습니다. `GameObject::Update()` 가 컴포넌트를 순회하고 렌더러가 그 안에서 드로우콜까지 부르는 흐름을 직접 짜 보니, Unity의 실행 순서 · 생명주기 콜백 · 컴포넌트 분리 원칙이 왜 그런 형태인지 이해했습니다.

- **공간 변환이 "외운 것"에서 "만든 것"이 됐습니다.** 월드·뷰·프로젝션을 직접 곱해 넘기고, 빌보드에서 카메라 방향으로부터 `right`·`up` 벡터를 만들어 사각형을 펼쳤습니다. 행렬 순서를 틀리면 화면이 어떻게 깨지는지 직접 겪은 것이 오래 남았습니다.

- **조명을 항으로 분해해 보고 셰이더가 읽히기 시작했습니다.** Ambient·Diffuse·Specular·Emissive 를 각각 별도 데모로 구현해, 각 항이 무엇을 담당하고 어떤 입력이 필요한지 분리해 확인했습니다.

- **애셋 파이프라인이 왜 필요한지 알게 됐습니다.** FBX를 런타임 파싱하지 않도록 Assimp로 읽어 자체 포맷(`.mesh`/`.clip`)으로 사전 변환하는 툴을 만들었고, 상용 엔진의 임포트 단계가 무엇을 위한 것인지 이해했습니다.

### 주의점 — 이 작업은 "엔진 개발"이 아니다

렌더링 파이프라인과 엔진 내부 로직을 **이해하기 위한 학습**이었습니다. 엔진을 만드는 일과 무엇이 다른지 적습니다.

- **만족시켜야 할 요구사항이 없었습니다.** 실제 엔진은 특정 게임의 요구에서 출발합니다 — 어떤 장르인지, 화면에 몇 개가 동시에 나오는지. 여기엔 그 출발점이 없었고 **"데모가 화면에 뜨면 성공"** 이 유일한 기준이었습니다. 무엇을 만들지 결정하는 과정 자체가 없었습니다.

- **예산이 없으니 트레이드오프 판단도 없었습니다.** 실제 엔진은 목표 하드웨어의 프레임·메모리 예산 안에서 **무엇을 포기할지** 계속 결정합니다. 인스턴싱을 구현했지만 "몇 개까지 감당되는가"를 재본 적이 없고, 재지 않았으니 버릴 것을 고를 일도 없었습니다. **기법을 아는 것과 예산 안에서 고르는 것은 다른 능력입니다.**

- **유지보수 대상이 아니었습니다.** 엔진 코드는 여러 사람이 오래 고쳐 쓰므로 API 안정성·확장 지점·하위 호환이 설계 요소가 됩니다. 여기서는 혼자 한 번 쓰고 끝이라 데모마다 구조를 갈아엎었고, **그 흔적이 그대로 남아 있습니다** — 데모 36개 중 28개는 이전 렌더 경로가 주석 처리된 채 방치되어 화면이 비어 있습니다.

- **검증 체계가 없었습니다.** 테스트도 프로파일링도 리그레션 확인도 없습니다. 눈으로 보고 넘어가는 것이 전부였고, 그래서 빌보드 데모의 시각적 결함이 오래 방치됐습니다. 원인은 파악했으나 적용은 하지 않았습니다.

- **다른 직군과의 접점이 없었습니다.** `AssimpTool` 은 툴 성격이지만 **쓸 사람이 저뿐이었습니다.** 실제 툴은 기획자·아티스트가 쓰고, 그때부터 사용성·에러 처리·워크플로우가 요구사항이 됩니다.

- **현실적인 규모를 다루지 않았습니다.** 데모는 오브젝트 수백 개 수준이라 컬링·LOD·스트리밍·메모리 관리처럼 **규모가 커져야 드러나는 문제**는 만나지 못했습니다.

**다루지 않은 기술 범위**: 그림자 매핑·후처리·PBR·지연 렌더링(조명은 단일 방향광 수준), 멀티스레드 렌더링·커맨드 리스트·리소스 배리어 같은 DX12/Vulkan 세대 주제.

> 증명하는 것은 **"파이프라인이 어떻게 도는지 안다"** 까지입니다.
> **"요구와 제약 안에서 엔진을 만들고 유지한다"** 는 다른 일이고, 그건 여기 없습니다.

## 4. 이 프로젝트를 더 강하게 만들려면

지금은 "이해했다"까지만 증명됩니다. **"측정하고 개선했다"** 로 올리려면 다음 중 하나면 충분합니다.

1. **인스턴싱 전후 비교 측정** — 같은 오브젝트 N개를 개별 드로우 vs 인스턴싱으로 그려
   드로우콜 수와 프레임 타임을 같은 조건에서 측정. 이 저장소에 이미 두 경로가 다 있어 바로 가능합니다.
2. **비활성 렌더 경로 복구** — `ModelRenderer::Update()` / `ModelAnimator::Update()` 를 되살려
   개별 렌더 경로와 인스턴싱 경로를 나란히 비교. 1번 측정의 준비 작업이 됩니다.
3. **`Animation::Save` 의 텍스처 경로 저장 완성** — 현재 `TODO` 로 비어 있어 저장 후 로드하면
   텍스처가 유실됩니다. 작은 범위지만 "직접 고친 것"이 됩니다.
